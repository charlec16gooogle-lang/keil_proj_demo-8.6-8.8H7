#### 2. 编译->烧录->文件名的作用
>[!NOTE]
>* **文件代表**：
 > * `.o` ：让CPU看懂的文件
 >* `.c` : 源文件，就是人编译的文件，
 >* `.axf` ：全局可执行的文件，已经有专门的内存地址之类的
 >* `.hex` ：从 `.axf` 提炼出的烧录机器码，最终的烧录文件，将程序写入控制器和存储器。
>* **F7的编译+F8的下载 的本质**:
  >F7进行的是首先编译+汇编--.c文件翻译为.o文件，然后是链接--通过给.o文件分FLASH和RAM的内存地址，合成.axf，提取.hex。然后F8负责下载到板子上，把代码>告诉板子。
>* **编译与下载**：
  >* **F7 (Build)**：增量编译。仅重新编译被修改过的 C 文件及其受影响的模块，然后重新链接生成 `.axf`/`.hex`。
  >* **Rebuild**：重新全编译。清除所有历史 `.o`/`.axf` 文件，对整个工程所有文件重新编译。(这两个概念的解释来自于AI)
  >* **关系**：修改 C 代码只是改变了文本文件，必须按下 **F7** 重新生成芯片能识别的机器码，再按 **F8** 下载才能在单片机上呈现新现象。
  >         <mark>--所以我们rebuild重新编译了以后需要重新F7+F8.</mark>

#### 3. keil5的配置：文件的添加和删除
对比<mark>删除 Include Paths </mark>与<mark>删除 Group 文件</mark>，找到.h.c等文件之间的关系
>[!NOTE]
>* **实验 1：移除 Include Paths 里的 `..\hardware\inc`**
 > * **结果**：F7 编译产生 4 个 errors，像`error: 'buzzer.h' file not found`、`error: 'led.h' file not found`。
 >* **原因**：`#include` 负责请求复制头文件内容，而 `Include Paths` 是编译器的<mark>导航地图</mark>。删去路径后，编译器在处理 `#include "buzzer.h"` 时找不到该头文件，所以会报错。
>* **实验 2：移除 Group 里的 `buzzer.c` 与 `led.c`**
  >* **结果**：F7 编译报 5 个 errors，像 `Error: L6218E: Undefined symbol buzzer_init (referred from main.o)`。
  >* **原因**：Include Paths 没问题，头文件声明存在，`main.c` 能正常编译生成 `main.o`；但因 `.c` 源文件被我们删掉了，未加入 Group 参与编译，链接器在组合所有 `.o` 时<mark>找不到函数的具体实现代码</mark>，所以会报错。
>* **总结**：
  >* **Include Paths (`.h`)**：相当于<mark>道路</mark>，告诉编译器有哪些函数和变量在哪里。缺了显示 `file not found`。
  >* **Group (`.c`)**：<mark>提供具体函数体</mark>，就是代码中每一个函数的方程内容，缺了显示 `Undefined symbol`。

### 二、 一些新概念本身及其作用

#### 1. `main.c` 模块化？
- **避免代码冗杂**：如果把所有逻辑（LED、蜂鸣器、按键、传感器）全写在 `main.c` 里，文件很快会膨胀到几千行，又难看，而且修改起来很困难，还容易影响到其他函数。

#### 2. `.h` 头文件与 `.c` 源文件
在 C 语言模块化时，<mark>`.h` `.c` 文件必须成对出现！</mark>
- **`.h`头文件**：
  - **防重复引用宏**：使用 `#ifndef ... #define ... #endif` 防止多个文件包含导致重复定义报错。
  - **函数声明**：告诉其他引用它的文件（如 `main.c`）：“这里有哪些函数可以被调用，需要传入什么参数”。
  - **宏定义与数据结构**：声明模块需要的全局常量（如 `#define LED_COUNT 4U`）与枚举数据类型。
- **`.c`（源文件 / “后厨实现”）**：
  - **包含关系**：必须在顶部 `#include "对应头文件.h"` 以及相关的底层硬件头文件（如 `led.h`, `buzzer.h`）。
  - **具体实现**：真正书写函数的具体代码（包含 `if/while/switch` 等控制语句）。     
- --（来自于AI的解释）我的理解就是.h是指明位置，这里调用这个函数，<mark>.c放这个函数的内容，而且这两个文件的名称要一样，还要让人一眼就看得出来这个函数的意思作用</mark>

#### 3. Keil 5 的编译与链接
当我们在vscode中创建了新的.c文件时，我们记得要在keil5中也加进去，以下是步骤：
- **添加路径**： `Options for Target -> C/C++ -> Include Paths` 中设置的目录路径。 --（这个是完全新开了一个文件夹的情况下,要记得这一步）
- **添加.c文件**：**必在 Keil 5 左侧 Group（如 `user` 分组）上右键 Add 添加 `.c` 源文件**！如果只包含了 `.h` 而没有把 `.c` 加入工程，编译会通过，但在 Link 阶段会直接报 `Undefined symbol` 错误。  --注：<mark>"add exsiting files"</mark>

#### 4. `enum` 在流水灯警报系统
- **定义方法**：
  ```c
  typedef enum {
      MODE_STANDBY = 0, /* 待机模式 */
      MODE_RUN     = 1, /* 运行模式 */
      MODE_ALARM   = 2  /* 报警模式 */
  } AlarmMode_t;
  ```
- **主要意义**：用具名单词取代数字 `0, 1, 2`。在外部调用 `alarm_sys_func(MODE_ALARM)` 时，代码读起来一目了然，极大地提升了可读性与维护效率。

#### 2：C语言的一些概念
> [!NOTE]
> 1. **变量定义和作用范围**
  > - **宏定义（预处理作用域）**：在整个代码中均可使用。
  >- **局部变量（局部作用域）**：

     >- `blink_led()` 函数内定义的 `uint16_t i = 0U;`：作用范围仅限于 `blink_led()` 函数内部，每次调用时创建，执行完毕即销毁。
>2. **函数声明与函数定义**
 >  - **函数声明**：
 >   比如`void blink_led(uint8_t led_num, uint16_t times, uint32_t delay_ms);`
 >    `void beep(uint32_t beep_ms);`
 >   *作用：提前告知编译器函数的名称、返回值类型和参数类型。*
 >  - **函数定义**：
 >   比如`void blink_led(...) { ... }` 与 `void beep(...) { ... }`
 >    *作用：真正用花括号 `{}` 编写函数的具体控制逻辑。*
>3. **形参，实参**
 >  - **形参**：函数定义与声明时小括号内的变量
 >  - **实参**：调用函数时真正传入的具体变量或数值
>4. **`for`、`while`、`if`、`switch`**
 >  - **`if`条件判断**：用于 `blink_led()` 开头的参数合法性校验——`if (led_num > LED_COUNT) return;`，防止传入超出 1~4 范围的非法灯号。
 >  - **`for`固定次数循环**：用于 `blink_led()` 内部——`for (i = 0U; i < times; i++)`，精确控制单颗 LED 亮灭交替重复执行指定的 `times` 次数。
 >  - **`while`条件 / 无限循环**：用于 `main()` 函数的主循环 `while (1)`，确保嵌入式系统上电后永不退出、持续运行；以及流水灯逻辑中按编号遍历 1~4 颗灯。
 >  - **`switch`**：用于作业四 `alarm_sys_func(mode)` 的状态机选择器，根据传入的 `mode` 参数在待机（`MODE_STANDBY`）、运行（`MODE_RUN`）与报警（`MODE_ALARM`）三种模式间快速切换。
  
#### 3. 流水灯报警系统 (alarm_sys)
> [!NOTE]
> - **具体操作**：
> 1. 在 `user/inc/` 新建 `alarm_sys.h`，在 `user/src/` 新建 `alarm_sys.c`。
> 2. **编写头文件 `alarm_sys.h`**：
>    ```c
>    #ifndef __ALARM_SYS_H
>    #define __ALARM_SYS_H
>    
>    #include "main.h"
>    
>    #define LED_COUNT 4U  /* 搬运宏定义，供灯光循环界限使用 */
>    
>    typedef enum {
>        MODE_STANDBY = 0,
>        MODE_RUN     = 1,
>        MODE_ALARM   = 2
>    } AlarmMode_t;
>    
>    void blink_led(uint8_t led_num, uint16_t times, uint32_t delay_ms);
>    void beep(uint32_t beep_ms);
>    void alarm_sys_func(AlarmMode_t mode);
>    
>    #endif
>    ```
> 3. **编写源文件 `alarm_sys.c`（后厨实现）**：
>    - 复制粘贴 `main.c` 里的 `blink_led` 和 `beep` 函数体，<mark>然后删掉</mark>。
>    - 写 `alarm_sys_func(AlarmMode_t mode)`这个函数，利用 `switch (mode)` 结构控制不同模式：
>      - `MODE_STANDBY`：静止不响，进行小额延时防止 CPU 空转。
>      - `MODE_RUN`：仅运行正常速度（250ms 延时）的流水灯。
>      - `MODE_ALARM`：流水灯加速（80ms 延时）并同步配合蜂鸣器（100ms 发声）进行间隔报警。--报警速度应该自由调节，有视觉上的明显差别就好了
> 4. **`main.c` 简化**：
>    - 顶部添加 `#include "alarm_sys.h"`。
>    - 删除 `USER CODE BEGIN PFP` 区域旧的 `blink_led` 和 `beep` 函数声明。
>    - 删除 `USER CODE BEGIN 4` 区域  `blink_led` 和 `beep` 函数具体实现代码  <mark>--要保留 `USER CODE` 边界注释标记。</mark>
>    - 在 `while(1)` 中补上我们写的函数`alarm_sys_func(MODE_ALARM);`。
> 5. 在 Keil 5 中将 `alarm_sys.c` 加到到 `user` 分组，按 `F7` 编译，按 `F8` 烧录并按下复位键验证硬件响应。

### 四、 我的常见报错

| 错误现象 / 提示 | 根本原因分析 | 标准排查与解决办法 |
| :--- | :--- | :--- |
| **`Undefined symbol blink_led (referred from main.o)`** | 只在 `.h` 里声明了函数，但没有把包含实现的 `.c` 文件加入 Keil | 在 Keil 左侧工程树对应的 Group 上右键 -> **Add Existing Files** 添加 `.c` |
| **`Cannot open source input file "alarm_sys.h"`** | 头文件路径未配置，或文件创建位置不在指定 Include Path 中 | 检查 Options for Target -> C/C++ -> Include Paths 是否包含了 `user/inc` 目录 |
| **`syntax error near '}'` / 编译缺少大括号** | 在清空 `main.c` 里的旧逻辑时，不小心把 `while(1)` 或 `main()` 的结尾 `}` 删掉了 | 仔细核对括号嵌套结构，确保只清空 `USER CODE BEGIN/END` 之间的内容 |
| **`git: 'add.' is not a git command`** | 命令行输错，`add` 与句点 `.` 之间缺少空格 | 严格输入 `git add .`（中间必须保留空格） |
| **`fatal: not a git repository`** | VSCode 终端当前所在的路径不在 Git 仓库根目录下 | 先执行 `cd <工程根目录>`（如 `cd keil_proj_demo`）切入正确的路径 |
